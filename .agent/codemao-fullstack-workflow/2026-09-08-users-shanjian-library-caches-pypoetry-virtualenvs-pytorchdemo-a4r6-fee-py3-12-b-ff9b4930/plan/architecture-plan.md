# Transformer 示例运行错误修复计划

## 1. 背景、目标与非目标

### 背景

执行 `apply/TranformerModel.py` 时，首个失败发生在 `MultiHeadAttention.split_heads`：

```text
RuntimeError: shape '[64, 100, 8, 512]' is invalid for input of size 3276800
```

调用链为训练循环 `Transformer.forward` -> `EncoderLayer.forward` -> `MultiHeadAttention.forward` -> `split_heads`。输入投影 `W_q` 的实际形状为 `(64, 100, 512)`，共有 `64 * 100 * 512 = 3,276,800` 个元素；代码要求的形状为 `(64, 100, 8, 512)`，共有 `26,214,400` 个元素，后者多了 `num_heads=8` 倍，因而无法重塑。

### 目标

1. 修正手写 Transformer 示例的多头维度不变量，使默认超参数 `d_model=512`、`num_heads=8` 能正常前向、反向和一次优化器更新。
2. 一并修复上述错误解除后必然到达的运行时错误与训练标签错位，保证该示例的训练和验证路径在张量形状、掩码与损失计算上自洽。
3. 将核心形状和训练步骤纳入自动化回归验证，避免同类错误仅在运行 100 轮示例时才被发现。

### 非目标

- 不改变为生产级机器翻译系统，不引入数据集、分词器、检查点或推理服务。
- 不重写为 `torch.nn.Transformer`；`apply/oneTransformerDemo.py` 保持独立示例，不作为本次修复对象。
- 不调整模型规模、优化器超参数或随机数据的教学用途。

## 2. 输入、证据与已确认假设

### 用户输入

用户提供了在 Python 3.12 虚拟环境运行 `apply/TranformerModel.py` 时的完整堆栈，要求分析该形状错误。

### 代码与环境证据

| 证据 | 结论 |
| --- | --- |
| `apply/TranformerModel.py:25` | `self.d_k` 被赋为 `d_model`，与“每个头的维度”注释和多头拆分公式矛盾。 |
| `apply/TranformerModel.py:28-31` | Q/K/V 投影均是 `Linear(512, 512)`，因此投影输出最后一维只能为 512。 |
| `apply/TranformerModel.py:62` | `view(B, S, H, d_k)` 要求 `H * d_k == d_model`。 |
| 运行参数 `B=64, S=100, H=8, d_model=512` | 正确的单头维度为 `d_k=512 / 8 = 64`；正确拆分形状是 `(64, 8, 100, 64)`。 |
| `apply/TranformerModel.py:184,219` | 模块注册为 `fc1`，前向却访问未定义的 `self.fc`；修正注意力后将抛出 `AttributeError`。 |
| `apply/TranformerModel.py:131-142` | 编码器创建了前馈网络和第二个归一化层，但前向没有使用它们，和文件内的组件声明不一致。 |
| `apply/TranformerModel.py:274,280` | 解码器输入和监督标签同为 `tgt_data[:, :-1]`，与“预测下一个词”的注释矛盾；标签应右移一位。 |
| `apply/TranformerModel.py:302` | 验证标签仅为 `val_tgt_data[:, :1]`，元素数量为 64，不能与 99 个时间步的 6,336 个 logit 行对齐。 |
| `pyproject.toml` | 依赖未声明 `torch`，而当前虚拟环境可导入 PyTorch `2.13.0`；新环境的可复现性不足。 |

### 已确认假设

- 该文件是以 batch-first 张量 `(batch, sequence, feature)` 实现的教学示例，现有嵌入层、位置编码和训练数据均采用这一约定。
- 词表索引 `0` 继续作为填充符；随机示例数据保持从 `1` 开始生成。
- 训练目标采用 teacher forcing：输入为目标序列去掉最后一个 token，监督为目标序列去掉第一个 token。
- 当前工作树中 `apply/TranformerModel.py` 有用户未提交的变更；实施时应在这些变更基础上精确修改，不回退它们。

## 3. 现状架构和约束

### 当前调用链

```text
随机 token 索引
  -> Embedding + PositionalEncoding
  -> EncoderLayer x num_layers
       -> MultiHeadAttention (当前首个失败点)
  -> DecoderLayer x num_layers
       -> 自注意力、交叉注意力、前馈网络
  -> 词表线性投影
  -> CrossEntropyLoss
```

`MultiHeadAttention` 是本文件中编码器自注意力、解码器自注意力及交叉注意力的共享组件，维度修复影响全部三条注意力路径。掩码在 `Transformer.generate_mask` 创建：源掩码为 `(B, 1, 1, S_src)`，目标掩码与 no-peak 掩码广播后为 `(B, 1, S_tgt, S_tgt)`。这两种形状可分别广播到注意力分数 `(B, H, S_query, S_key)`。

### 技术与构建约束

- Python 要求为 `>=3.12`；当前故障环境为 Poetry 虚拟环境。
- 代码使用 PyTorch 模块和张量 API；实测已安装版本为 `2.13.0`。
- 当前没有 `tests/`、pytest 配置、CI、部署配置、持久化、网络接口或数据库。
- 未发现 `AGENTS.md`、`CLAUDE.md`、`.specify/memory/constitution.md` 或 `.specify/extensions.yml`，因此没有额外项目规范、架构原则或前后置钩子需要执行。

### 关键不变量

1. `d_model % num_heads == 0`。
2. `d_k = d_model // num_heads`。
3. Q/K/V 拆分前后的元素数量相同：`B * S * d_model == B * S * num_heads * d_k`。
4. 合并多头后最后一维恢复为 `d_model`，才能输入输出投影层。
5. 对每个 batch，训练 logit 行数和目标标签数均为 `B * (S_tgt - 1)`。

## 4. 技术决策及备选方案

### 决策 1：按标准公式计算每头维度

- **决策**：将 `MultiHeadAttention.__init__` 中的 `self.d_k` 改为 `d_model // num_heads`，保留已有可整除断言；必要时将错误信息补充为实际的 `d_model` 与 `num_heads`。
- **理由**：Q/K/V 投影维度固定为 `d_model`，只有将它均分到 `num_heads` 才满足 `view` 的元素守恒。默认配置将产生 `(64, 8, 100, 64)`，缩放因子也随之正确变成 `sqrt(64)`。
- **备选方案**：把 Q/K/V 线性层输出扩张到 `num_heads * d_model`。这会把模型参数和注意力宽度扩大八倍，破坏 `W_o` 与残差层的现有 `d_model=512` 契约，且不是多头注意力的目标，故不采用。
- **证据**：`apply/TranformerModel.py:25,28-31,62` 及用户堆栈中的实际元素数量。

### 决策 2：统一最终词表投影的成员名

- **决策**：将最后线性层采用单一清晰名称（建议 `self.output_projection`），并在 `forward` 使用同一成员；在一次集中修改中删除旧的 `fc1` 命名引用。
- **理由**：`self.fc` 当前不存在，注意力修复后输出阶段无法运行。语义化名称能与编码器/解码器内部前馈层区分。
- **备选方案**：仅将 `self.fc(dec_output)` 改为 `self.fc1(dec_output)`。可运行但仍保留含糊命名，且不利于教学代码区分不同线性层，故不作为首选。
- **证据**：`apply/TranformerModel.py:184,219`。

### 决策 3：完成编码器声明的前馈子层

- **决策**：在编码器注意力残差归一化后执行 `feed_forward`，再通过 dropout、第二个残差和 `norm2` 输出。
- **理由**：该层已构造前馈网络和第二归一化层，而目前参数永远不参与计算，模型结构与文件注释“每个层包含自注意力和前馈网络”不一致。
- **备选方案**：删除未使用的前馈网络和 `norm2`。这会令编码器与声明的 Transformer 结构不一致，且丢失现有设计意图，故不采用。
- **证据**：`apply/TranformerModel.py:92-102,128-142`。

### 决策 4：使用右移标签并统一训练和验证损失

- **决策**：定义 `decoder_input = tgt[:, :-1]`、`target = tgt[:, 1:]`；训练与验证均把 `(B, S-1, V)` 输出和 `(B, S-1)` 标签展开后计算同一损失。可提取小型辅助函数以消除两处重复，但不改变公共模型接口。
- **理由**：这符合自回归 next-token 预测，且避免验证路径目前的元素数不匹配。
- **备选方案**：维持标签为 `tgt[:, :-1]`。虽然形状相同，但会训练模型复制当前 token，违背代码注释和目标掩码的因果预测意图，故不采用。
- **证据**：`apply/TranformerModel.py:274-302`。

### 决策 5：使演示可测、可复现，并声明运行依赖

- **决策**：将训练/验证演示封装为可配置的函数，并置于 `if __name__ == "__main__":` 下；新增轻量 pytest 测试。将与已验证运行环境一致的 PyTorch 依赖写入 Poetry 配置，版本下界以实际支持 Python 3.12 的版本为准并同步更新 lockfile。
- **理由**：当前导入模块会立即开始 100 轮训练，测试无法安全导入类；同时从项目元数据安装时并不能保证获得 `torch`。默认脚本仍保留原有演示行为，测试可以使用小参数快速执行。
- **备选方案**：测试通过 subprocess 运行整个脚本。它需分配默认规模的 6 层、512 维模型并训练 100 轮，速度慢且不能隔离形状、掩码和梯度断言，故不采用。
- **证据**：`apply/TranformerModel.py:247-303`、`pyproject.toml` 和当前无测试文件的仓库清单。

## 5. 目标架构、组件与依赖

修复后仍维持单文件教学模型，职责边界如下：

| 组件 | 职责 | 依赖 |
| --- | --- | --- |
| `MultiHeadAttention` | 验证并完成 `d_model -> H * d_k -> d_model` 的 Q/K/V 注意力变换 | PyTorch、数学缩放、广播掩码 |
| `EncoderLayer` | 自注意力和前馈子层，各自具有残差、dropout、归一化 | `MultiHeadAttention`、`PositionwiseFeedForward` |
| `DecoderLayer` | 因果自注意力、源序列交叉注意力、前馈子层 | 编码器输出和两类掩码 |
| `Transformer` | 词嵌入、位置编码、掩码生成、层堆叠和词表 logit 投影 | 前三类组件 |
| 训练/验证辅助函数 | 构造右移输入与标签，计算损失并控制单次迭代 | `Transformer`、`CrossEntropyLoss` |
| `tests/test_transformer_model.py` | 小尺寸合约、回归与梯度验证 | 模型模块，不触发训练脚本 |

依赖顺序为：注意力维度契约 -> 编码器及输出投影正确性 -> 训练标签和设备安全的掩码 -> 导入隔离 -> 自动化测试和依赖声明。

## 8. 数据流、异常处理与恢复

### 正常数据流

1. 输入 token 经嵌入和位置编码形成 `(B, S, d_model)`。
2. 每个注意力层的三组投影拆为 `(B, H, S, d_model/H)`；注意力分数为 `(B, H, S_query, S_key)`。
3. 源填充掩码或目标填充加 no-peak 掩码广播到分数后，softmax 与 V 相乘并合并回 `(B, S, d_model)`。
4. 解码输出经词表投影得到 `(B, S_tgt-1, V)`；与右移目标 `(B, S_tgt-1)` 计算交叉熵。

### 防御与恢复

- 保留 `d_model % num_heads == 0` 的构造期失败，避免不合法模型在 `view` 时才报难以定位的错。
- 在 `split_heads` 中可显式检查输入最后一维等于 `self.d_model`，错误信息应报告实际形状和期望值；这是开发时断言，不改变正常路径。
- `generate_mask` 的 no-peak 张量必须在 `tgt.device` 创建，保证 CPU/GPU 两种运行环境均可广播；保持布尔掩码并使用布尔取反/比较表达屏蔽条件。
- 对位置编码长度，在输入序列超过 `max_seq_length` 时给出明确 `ValueError` 或断言提示，避免加法阶段出现不明确的维度错误。
- 单步训练发生异常时不写入模型文件或外部状态；恢复方式是修正输入维度/长度或参数后重新执行该演示。

## 9. 实施阶段和依赖顺序

### 阶段 1：修复共享注意力和层内计算

- **目标**：恢复所有注意力路径的维度守恒，并令编码器执行其已声明的两个子层。
- **涉及文件**：`apply/TranformerModel.py`。
- **实施**：将 `d_k` 计算为整除结果；审查 `split_heads`、`combine_heads` 和缩放分母与此值一致；补上编码器前馈残差和第二归一化。
- **前置依赖**：无。
- **接口与数据变化**：无公共签名变化；中间单头张量最后维度从错误的 512 修正为 64。
- **验收**：默认形状的前向不再在 `view` 失败；小尺寸配置可覆盖 self-attention 和 cross-attention。
- **风险与回滚**：共享组件影响三处注意力调用。若出现形状回归，回滚该阶段的局部变更并以维度测试定位，不回退用户已有的无关修改。

### 阶段 2：修复输出、标签和设备一致性

- **目标**：使前向输出、训练、验证和掩码均能完成正确的一次迭代。
- **涉及文件**：`apply/TranformerModel.py`。
- **实施**：统一输出投影成员名；使用右移标签；训练和验证复用同一损失展平规则；使 no-peak 掩码与 `tgt` 同设备；为超长序列添加清晰错误。
- **前置依赖**：阶段 1。
- **接口与数据变化**：模型调用签名不变；训练监督从复制当前 token 修正为预测下一个 token。
- **验收**：`loss.backward()` 与 `optimizer.step()` 无异常；验证损失的 logit 行数和标签数一致；在 CUDA 可用时的 GPU 前向测试通过，否则在测试中跳过并明确原因。
- **风险与回滚**：右移标签会改变演示损失数值，这是预期语义修复；不以旧数值作为回归基线。

### 阶段 3：建立可测试入口和回归覆盖

- **目标**：避免导入副作用，并使核心数学契约可快速验证。
- **涉及文件**：`apply/TranformerModel.py`、`tests/test_transformer_model.py`、`pyproject.toml`、`poetry.lock`。
- **实施**：将演示训练置于主程序入口下并提取最小可测函数；声明 PyTorch 依赖并使用 Poetry 更新锁文件；增加 pytest 入口和测试。
- **前置依赖**：阶段 1 和阶段 2。
- **接口与数据变化**：脚本直接执行兼容；导入改为无训练副作用。
- **验收**：测试导入不打印 epoch、不创建训练循环；锁定环境安装后可导入 `torch`；pytest 全部通过。
- **风险与回滚**：锁文件更新可能引入转移依赖变化。提交前审查 lockfile diff，只保留 PyTorch 解析所需变更；必要时将元数据声明与代码修复拆为独立提交。

## 10. 测试矩阵与验收标准

| 测试 | 配置/输入 | 断言 |
| --- | --- | --- |
| 单头维度拆分 | `d_model=512, num_heads=8`，输入 `(2, 3, 512)` | `split_heads` 输出 `(2, 8, 3, 64)`，`combine_heads` 输出恢复 `(2, 3, 512)`。 |

| 导入行为 | 导入模块 | 不启动 100 epoch 训练、不产生训练日志。 |

验收命令为项目 Poetry 环境中的 `python -m pytest -q`，并使用一个受控的小配置执行训练函数或脚本的单步 smoke test。默认 100 epoch 演示不作为每次自动化测试的必跑项。

## 11. 可观测性、安全与性能

- **可观测性**：训练函数仅保留每轮损失输出；测试以张量形状、有限值和梯度存在性提供可诊断信号。异常信息必须包含不满足的维度或长度。
- **安全与合规**：随机合成 token 不含用户数据；不新增网络访问、日志上传、凭据、文件持久化或外部服务。
- **性能**：默认模型约 6 层、512 维、长度 100，训练成本显著；自动测试改用小尺寸、单步执行，防止测试套件因示例规模变慢。`view` 前保持 `contiguous()` 的现有正确用法，避免不必要拷贝或布局错误。

## 12. 发布、迁移和回滚

这是本地示例项目，没有部署、线上迁移、版本化模型产物或数据迁移窗口。

实施以小的、可审查的提交进行：先共享注意力与层修复，再训练/验证修复，再测试及依赖元数据。每步运行对应测试；若失败，使用版本控制仅回退该步骤引入的改动，保留用户工作树中已有的独立改动。发布前在 Poetry 的干净环境执行测试，确认依赖解析包含 PyTorch。
